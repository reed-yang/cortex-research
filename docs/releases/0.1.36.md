# Product 0.1.36

Status: deployed on the operator host on 2026-10-08; isolated lifecycle,
21 -> 22 upgrade and rollback rehearsal, and production upgrade passed.
Published as GitHub release `v0.1.36`, which also carries 0.1.31 to 0.1.35.
The fallback was then enabled there; its first run took the backlog of 83
recommendations after the rules turned 6 arXiv-linked blogs into papers.

Recommendations that XHS identification and link search leave unimportable
get a weekly fallback review, and the operator can exclude and restore
recommendations. Control moves to schema 22; the worker `hermes-0.15.0-gen10`
is unchanged.

**Rules.** A blog recommendation whose link is an arXiv abs, pdf or html page
becomes a paper with that arXiv ID; when another paper of the same note already
has that ID, the blog is excluded as a duplicate instead. The rules make no
network call and import nothing.

**Weekly review.** Once a week, at most `fallback_weekly_cap` (default and
maximum 100) remaining recommendations are reviewed by `fallback_model`
(default `gpt-6.1-sol` at effort `xhigh`) with web search: one call per item,
never repeated, counted against the `gpt` daily cap. A proposed blog link or
arXiv ID is applied only after Cortex fetches the page itself and its title
matches; a link to a paper host or PDF is never taken as a blog. A verified
blog is queued for import; a corrected paper is never imported and no Capture
is staged. The model may also exclude an item with a reason. What it cannot
decide is left to the operator, listed in a new Inbox section and summarized
in one Telegram message per run with a link to the Web Inbox. The review runs
inside the `xhs-drain` tick and only with `[xhs] fallback_enabled = true`,
which is off by default, so the upgrade alone changes no data and makes no
call. See [the plan](../plans/xhs-recommendation-fallback.md) and
[the runbook](../runbooks/xhs.md#recommendation-fallback).

**Exclusion and review display.** A recommendation row in the Library shows
its review: excluded with the reason, corrected automatically, paper identified,
not on arXiv, or needs your decision. The operator can exclude an unimported
row with a reason and restore it; import refuses an excluded row, and a
restored row is never reviewed automatically again. The Control API adds
`review` to every recommendation, `POST .../recommendations/{id}/exclude` and
`.../restore`, `GET /api/v1/xhs/recommendations?review=needs_operator` and a
`fallback` block in `GET /api/v1/xhs/status`; the CLI adds
`cortex xhs fallback status` and `cortex xhs fallback run --dry-run|--yes`.

Two new child operations carry the provider I/O: `xhs_fallback_decide`
receives only `sub2api-gpt`, and `xhs_fallback_verify` receives no credential.
With the review enabled, the Responses endpoint receives each reviewed
recommendation's fields and at most 12,000 characters of its cited text, the
provider's web search receives the model's queries, proposed pages receive a
title fetch, and Telegram receives a count, up to three titles and the Web
Inbox link ([provider data disclosure](../runbooks/xhs.md#provider-data-disclosure)).

Migration 22 adds three tables, `xhs_recommendation_reviews`,
`xhs_fallback_runs` and `xhs_fallback_items`, and changes no existing table.
`state_archive.py` accepts schema 22, so a 21 -> 22 upgrade gets a baseline
archive and recovery script. As for 0.1.30, the schema change needs the
isolated rehearsal before production: a fresh install, a 21 -> 22 upgrade
with a baseline archive and backup proof, the rollback refusal at schema 22,
and a restore of the schema 21 state and configuration. Products before 0.1.36
refuse the four new `fallback_*` keys in `[xhs]`, so a rollback must restore
`config.toml` with the state. The Python dependency closure is unchanged.
