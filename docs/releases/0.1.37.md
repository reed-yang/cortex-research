# Product 0.1.37

Status: selected; build and production upgrade pending.

Readings publication no longer stops cortexd after a macOS update renumbers the
library's volume. The publication journal binds the library root and each
published paper directory as `[st_dev, st_ino]`, and macOS assigns `st_dev` in
the order it finds disks at boot. On the operator host the 27.0.1 update moved
the Data volume from 16777231 to 16777234 with every path and inode unchanged,
and cortexd refused to start until the journal was rebound by hand.

Startup now records the library's volume UUID in the journal while the binding
matches. When only `st_dev` differs and the path, corpus, root inode and
recorded volume UUID match, it rewrites the device of the root and of each
paper directory whose inode and volume still match, in one transaction, and
logs the change. A journal without a recorded UUID, a different volume or a
different inode is still refused, and a replaced paper directory keeps its old
identity and conflicts as before. See
[the runbook](../runbooks/readings-publication.md#journal-indexing-and-rollback).

The Control schema stays 22 and the worker `hermes-0.15.0-gen10` is unchanged,
so an upgrade from 0.1.36 is code-only. A rollback to 0.1.36 ignores the
recorded UUID and refuses a renumbered device as before.
